Velocita: Building a Replicated Trading System on Home Hardware

2026-10-27·Vishal Jha·GitHub Source

On October 15, a Raspberry Pi on my desk voted to buy $12.69 of SOL. Three seconds later the trade was on the Solana blockchain. Over the next three hours, with nobody touching anything, its cluster settled 16 real swaps, and every one matched the blockchain to the billionth of a SOL.

It lost 95 cents. It also stopped on an order whose outcome it could not verify. The run tested execution and accounting; it did not demonstrate a profitable strategy.

Measurements cover different scopes: 25 applied live intents for commit latency, 16 successful swaps for block inclusion, and an in-memory reducer benchmark on an Apple M5 Pro (125 ns p50, 167 ns p99; no Raft, WAL or network). The 4–7 s restart times came from a halted-cluster rolling upgrade. Benchmark records · restart record.

1. The problem

An automated trading system has to handle failures beyond the signal itself:

Crashes mid-send
Restart must neither lose the order nor send it twice.
Ambiguous venue responses
"Failed" doesn't always mean "didn't happen".
Limits outside the strategy
The kernel must enforce spending and loss limits even if signal code is wrong.
Cheap hardware
Two mini PCs and a Pi on home Wi-Fi.

I wanted to test these failure boundaries with a real $25 account and hardware I could operate at home.

2. The idea: separate deciding from doing

Money and decisions live in one deterministic state machine that three machines replicate with Raft. Everything that touches the outside world runs separately, acts only on committed state, and brings back evidence.

3. The SD card that couldn't keep up

The chart compares V1.1 at 5 commands/s on one Pi with 25 sparse live intents across three machines. It shows the project’s history, not a controlled speedup from one code change.

Three voters on one Pi did ~9 fsyncs per command through one SD card, and the Raft thread waited on every one. At 20 commands/s the cluster lost its leader.

The WAL change moved writes and syncs to a writer thread. The Raft thread hands it sealed 4 KiB blocks over a lock-free ring; it can still face backpressure when the arena fills.

bool push(const T& value) noexcept {
    const auto head = head_.load(std::memory_order_relaxed);
    const auto tail = tail_.load(std::memory_order_acquire);
    if (head - tail >= Capacity) return false;      // full: refuse, never overwrite
    slots_[head & (Capacity - 1)] = value;
    head_.store(head + 1, std::memory_order_release); // publish
    return true;
}

Why asynchronous storage needed a Raft change

The upstream library assumes synchronous persistence and counts the leader's own vote when an entry is appended. An asynchronous integration must change that assumption. This hypothetical failure shows why; it was not an observed loss in Velocita:

sequenceDiagram participant L as Leader participant F1 as Follower 1 participant F2 as Follower 2 L->>F1: entry 42 (leader's copy only in memory) F1-->>L: durable Note over L: majority, commit 42 Note over L: crash; unsafe integration restarts without 42 Note over F1: briefly unreachable L->>F2: elect a leader: neither has 42 Note over L,F2: committed entry 42 is gone
ADR 0006 · the fix
A pinned fork adds a durable_idx hook: the leader's vote counts only up to what is really on disk. The build refuses to compile without the patch.

This example assumes the restarted node is allowed to serve despite losing its volatile suffix. Current Velocita separately refuses recovery when a persisted commit index exceeds the recovered log. The durable-quorum patch prevents the unsafe acknowledgement in the first place.

4. Fixed budgets for kernel state

The deterministic reducer uses fixed-size tables, and the retained log and WAL use startup-allocated arenas. Full tables refuse admission; a full WAL arena creates backpressure. The surrounding node still allocates for proposal payloads, peer messages and persistence jobs, so the whole Raft path is not allocation-free.

Every message is tagged with a key derived per direction and per cluster, so a captured frame can't be replayed backwards or into another cluster. Deployed service credentials are placed in tmpfs, rather than the voter’s SD-card data directory. The owner’s Keychain and downloaded API-key file are separate custody responsibilities.

ADR 0019 · decode, don't simulate
A simulation shows what a transaction would do now. Decoding proves what the signature allows: which accounts, how much at most, and the minimum that must arrive.

9. Effect 25: the exchange said "failed"

sequenceDiagram participant G as Gateway participant T as Exchange participant C as Solana G->>T: execute buy (effect 25) T-->>G: failed, executed 0, NO transaction hash Note over G: hold the $12.69 until outcome is proven Note over G: stop after 3 min G->>C: later recovery checks expiry and history Note over G: chain_unproven; exact failing check not logged

A failed status without a transaction hash was not enough to release the reservation. If an order could still execute later, reusing its reserved cash would understate the exposure.

A later wallet-history capture found a candidate transaction in the same second as the order. It landed in slot 457,481,187, failed inside a DEX, and changed neither the owner’s SOL nor USDC balance. The archived analysis attributed it to effect 25, but the published reduced records do not prove a match to the prepared payload or explain which recovery check returned chain_unproven. That linkage still needs verification before settlement. The last recorded recovery left the reservation held. Evidence and limits.

ADR 0027 · unknown is a state
"We don't know" keeps the money reserved. Once a signature might exist, only the chain can close it.

The diagram shows the intended retained-log catch-up path. The measured 4–7 s times above came from graceful rolling restarts with trading halted and no entries committed while a voter was away. They are not power-cut or live-trading failover timings. During the earlier October 15 upgrade, the NUCs formed a quorum while the Pi took minutes to start, and all three later converged at index 17.

A voter can catch up from entries the leader still retains. Once it falls behind the compacted prefix, recovery needs operator repair from an archive. Snapshot-install components exist, but the integrated online installer remains unimplemented.

11. Where the 95 cents went

fees 40 bp

The Binance reference moved about −2 bp per round trip on average (grey). The remaining execution difference is measured against another venue; it is not a direct spread measurement.

The strategy served as an execution test load. The replay windows had negative aggregate returns before costs, and this live run lost money. At the observed costs, a round trip needed roughly a 1% favorable move to break even. These samples did not demonstrate an edge; they also do not prove that every strategy on this venue must lose.

What I took away

  • Measure first. Every fix above started as a number that looked wrong.
  • Recheck assumptions after an optimization. Moving WAL syncs off-thread required an explicit durable-quorum boundary, checked with targeted persistence tests.
  • Keep uncertainty explicit. An unresolved order must remain reserved until the evidence supports settlement, even if that stops trading.

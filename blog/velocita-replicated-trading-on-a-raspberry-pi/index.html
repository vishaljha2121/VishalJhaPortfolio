Velocita: A Replicated Trading System on a Raspberry Pi That Refused to Believe the Exchange

2026-10-27·Vishal Jha·GitHub Source

On October 15, a Raspberry Pi on my desk voted to buy $12.69 of SOL. Three seconds later the trade was on the Solana blockchain. Over the next three hours, with nobody touching anything, its cluster settled 16 real swaps, and every one matched the blockchain to the billionth of a SOL.

It lost 95 cents. The most interesting thing it did all night was refuse to believe the exchange.

1. The problem

Real money breaks things a trading script never notices:

Crashes mid-send
Restart must neither lose the order nor send it twice.
An exchange you can't fully trust
"Failed" doesn't always mean "didn't happen".
A strategy you shouldn't trust
A signal bug must not be able to drain the account.
Cheap hardware
Two mini PCs and a Pi on home Wi-Fi.

These are the same failures that cost real trading firms money. I wanted to see if the textbook answers could hold all the way down to a $25 account on a Raspberry Pi.

2. The idea: separate deciding from doing

Money and decisions live in one deterministic state machine that three machines replicate with Raft. Everything that touches the outside world runs separately, acts only on committed state, and brings back evidence.

One trade passes through five hands, and none can complete it alone:

3. The SD card that couldn't keep up

Commit latency, p50
V1.1 · one Pi
396 ms
V2 · live
126 ms

Three voters on one Pi did ~9 fsyncs per command through one SD card, and the Raft thread waited on every one. At 20 commands/s the cluster lost its leader.

The fix: the Raft thread never touches the disk. It hands 4 KiB blocks to a writer thread over a lock-free ring.

bool push(const T& value) noexcept {
    const auto head = head_.load(std::memory_order_relaxed);
    const auto tail = tail_.load(std::memory_order_acquire);
    if (head - tail >= Capacity) return false;      // full: refuse, never overwrite
    slots_[head & (Capacity - 1)] = value;
    head_.store(head + 1, std::memory_order_release); // publish
    return true;
}

…which broke Raft

The Raft library counts the leader's own vote as soon as an entry is appended. With async writes, that vote arrived before the entry was on disk:

sequenceDiagram participant L as Leader participant F1 as Follower 1 participant F2 as Follower 2 L->>F1: entry 42 (leader's copy only in memory) F1-->>L: durable Note over L: majority, commit 42 Note over L: crash, restart without 42 Note over F1: briefly unreachable L->>F2: elect a leader: neither has 42 Note over L,F2: committed entry 42 is gone
ADR 0006 · the fix
A pinned fork adds a durable_idx hook: the leader's vote counts only up to what is really on disk. The build refuses to compile without the patch.

4. Memory that never grows

Nothing on the Raft path asks the OS for memory after start-up. Every object has a size fixed at compile time, and "full" is a typed refusal, never a slowdown or an out-of-memory kill.

ADR 0022 · budgets are compile errors
The snapshot must fit one 64 KiB message. As a runtime check, growing a struct would surface in production as a snapshot that no longer fits; as a static_assert, the build fails on both CPUs and whoever adds the field decides what to give up.

6. The gateway that stopped itself, twice

The gateway stops when anything looks off, because a stop might hide an order in flight. That paranoia surfaced two bugs:

7. One process holds the key, and trusts no one

The gateway talks to the internet, so it never sees the key. The signer re-checks everything itself before signing:

flowchart LR A["sign request"] --> B["re-read Raft:
effect prepared?"] B --> C["decode the transaction:
amounts, fee, DEX match?"] C --> D["authority proof
from Raft"] D --> E["journal, then sign"]
ADR 0019 · decode, don't simulate
A simulation shows what a transaction would do now. Decoding proves what the signature allows: which accounts, how much at most, and the minimum that must arrive.

8. 16 out of 16, to the atom

Every amount in Velocita is an integer count of an asset's smallest unit, called an atom:

Same bits everywhere
Floats round differently on Intel and ARM; integers can't fork the replicas.
Equal to the chain
Solana stores balances in these units, so a settlement compares with ==, no tolerance.

9. Effect 25: the exchange said "failed"

sequenceDiagram participant G as Gateway participant T as Exchange participant C as Solana G->>T: execute buy (effect 25) T->>C: submit Note over C: lands in slot 457,481,187 and fails T-->>G: failed, executed 0, NO transaction hash Note over G: nothing to verify, so hold the $12.69 Note over G: stop after 3 min Note over G,C: new on-chain proof built for "never executed" Note over G: proof refuses

Believing the exchange would have recorded a transaction that did reach the chain as one that never did. Had it succeeded late, the same cash could have been spent twice. I later found it in the wallet's history: it landed in the same second the order was created, failed inside a DEX, and moved none of our money.

ADR 0027 · unknown is a state
"We don't know" keeps the money reserved. Once a signature might exist, only the chain can close it.

11. Where the 95 cents went

Cost of one round trip, ~94 bp
fees 40 bp
exchange price 52 bp
The market itself moved only −2 bp (grey) between buy and sell.

The strategy was a test load with no edge, and replays had said so. The live run measured the cost: a one-second strategy here needs a ~1% move just to break even. The system worked; the economics never could.

What I took away

  • Measure first. Every fix above started as a number that looked wrong.
  • Fixes create bugs. The 490× speedup quietly broke Raft; only a test of every crash point caught it.
  • Refusing is a feature. The best thing it did with real money was say "I can't prove that".

Velocita Tape: A Verifiable Recording of a Public Market-Data Feed

2026-11-20·Vishal Jha·GitHub Source

An exchange sends its order book as a stream: a snapshot, then changes. Every client folds those changes into its own copy of the book. If a client misses or misapplies one message, its book is wrong, and nothing on the screen says so. The exchange only knows what it sent. One client only knows what it received. Nobody can show whether the feed was complete, correct, timely and the same for everyone.

Velocita Tape measures those things from outside. Three machines on my desk (two mini PCs and a Raspberry Pi 5) each hold their own connection to the public, no-login feed of the twelve tokenized-stock books in True Markets' Orderbook Arena. Every frame they receive goes into one log that the three machines replicate with Raft. Each machine rebuilds all twelve books from that log, bit for bit the same, and the cluster signs the log's Merkle root every minute. Anyone with the log and three public keys can check every number below on their own computer, with no network and no trust in my machines.

It never trades. It reads only the documented no-login channels, holds no exchange credentials, and a build check proves that no tape binary links any order-entry or signing code.

Scope: 13.8 recorded hours on 2026-11-12 with all three machines, and 7.2 hours on 2026-11-13 with two machines after one failed. All the machines sit on one home network, so the results describe delivery to one location, and only the no-login feed tier. Every figure links to the output that produced it in the evidence directory, regenerated from the archived logs at the published commit.

1. What a single client cannot see

A feed client sees one stream from one place. To say something about the feed itself, you need more than one vantage point and a record nobody can quietly edit. I wanted to answer five questions:

Complete
Did every subscriber get every update?
Correct
Is the book you rebuild from it actually the book?
Timely
How far apart do copies arrive?
Live
How long can a healthy book stay silent?
The same for everyone
Did any two machines get different bytes for one message?

This sits on top of Velocita, my replicated trading system on the same three machines. The tape reuses its Aeron transport and its Raft fork with the durable-quorum patch. It runs as a separate Raft group with its own ports, keys and data, so it can never send an order.

Each recorder keeps every frame byte for byte, watches the sequence numbers for gaps, and submits each frame, sealed with an HMAC, to all three voters over Aeron. The voters put everything in one order through Raft. A pure reducer, which reads no clock and makes no system calls, then decides three things for every message:

  • A verdict. Every update gets exactly one: identical at 3, 2 or 1 recorders, or divergent (different bytes for the same message). It closes when all three have reported, or 5 ticks after the first copy, so a silent machine can't hold it open.
  • The book. All twelve books are rebuilt in integer units of 10−9, so every machine computes the same bits.
  • Integrity checks. Crossed books, trades outside the book, and snapshots that disagree with updates are recorded but never change a book.

A capture before writing any code, then the first live runs, settled the feed's rules. Some of them were not what the docs said:

What the feed doesWhat it changed
Updates replace whole levelsA level's new total, not a delta. The live field is order_count; the spec says depth. (D-03)
A snapshot shares its number with the next updateKeyed on sequence number alone, a snapshot and an update looked like two versions of one message, so the verdict key includes the message kind. (D-13)
A snapshot is a reply, not a broadcastTwo recorders subscribing 49 ms apart got different snapshots with the same number. Each snapshot is now its own verdict; only updates are compared. (D-25, D-26)
Up to 9 decimal placesPrices and sizes are integers at a fixed scale of 10−9, never floats. (D-04)

I also built smaller pieces instead of reusing big ones. The tape has its own compact Raft replica and write-ahead log rather than a fork of the trading kernel (D-05, D-06). It has its own WebSocket client over OpenSSL (D-11), and a JSON scanner that reads only the fields it needs and never allocates (D-12). An independent Python reference implementation checks the reducer, including on two real connections replayed through both.

3. Turning a log into proof

Agreement between three machines I own proves little if I can edit the record afterwards. So every log entry is a leaf in an RFC 9162 Merkle tree. Each minute, the voters sign the tree's root with Ed25519 keys that were generated on their own machines and have never left them. A head is published once two of the three have signed. Segments rotate every 4 hours, and each segment's first entry names the previous segment's last signed head, so the segments form one chain:

head 44460" --> S2["Segment 1794499200
18:17–19:48 UTC

The verifier needs only the log, the heads and the public keys. It replays every entry through the same reducer the voters run, rebuilds the tree, and checks every head, the consistency between consecutive heads, and the link to the previous segment. This is the real output for the 16:00 segment:

$ velocita-tape-verify --wal wal.log --heads heads --incarnation 1794499200 \
      --previous-head ../68934737119228/heads/head-44460.json --key head-{1,2,3}.pub.pem
{"ok":true,"entries":121569,"heads_verified":75,"tick_spacing_flags":2,"symbols":12,
 "root":"6220035433496c15c2b39d0291a132f262ba5d6e24af9b66718c2c6ffbffbd64",
 "previous_segment":{"incarnation":68934737119228,"tick":44460,"linked":true}}

Change one byte anywhere and it fails, naming the entry and the check that broke. The two tick_spacing_flags are the two times the tape was stopped. The verifier reports gaps like these instead of hiding them.

4. Home Wi-Fi broke what localhost never did

Everything passed on one machine. Then it went live on 2026-11-12 at 00:07 UTC over home Wi-Fi with Tailscale between the hosts. About 25 minutes later, each host was sending 1 to 2.5 MB/s, pings between hosts were losing 90–100% of packets, and Raft had gone through 36 terms. The books were still correct. The tape was just flooding the network it shares.

Resends that grew with the square of the RTT
The leader resent every unacknowledged entry on every heartbeat. On a slow link that fed on itself. Now each entry crosses once, with per-follower byte budgets and backed-off probes (D-42, D-43).
Aeron multiplying loss
With a peer flapping, the Pi recorder’s embedded driver sent 1.22 GB in four minutes; the recorder itself could offer about 100 KB/s. Aeron’s frames were also bigger than the tunnel’s MTU; they now fit (D-53, D-56).
A log that outgrew memory
The log grows about 30 KB/s, and every voter held all of it. The Pi was killed for memory in a loop, and that set off the flood. Fix: 4-hour segments chained by signed heads (D-54, D-55, D-58).
A recorder racing the feed
The Pi got about 60% of the frames the NUCs got, nearly all of the shortfall in DEPTH. The feed handles one control request at a time, and my back-to-back unsubscribe and subscribe got rejected. Now requests are queued and the subscriptions are checked again (D-47).

The last safety net is a per-host watchdog. If a host's Tailscale traffic stays above 600 KB/s for a minute, it stops the tape, and it restarts the tape once the link has been quiet for 5 minutes. The tape's own worst case is about 200 KB/s, so a trip means something has gone wrong. Each fix came with a test that fails without it, usually a slow or lossy simulated link. Before the fix, sending 303 entries to a follower over a 400 ms link took 5,314 sends; now it takes at most 1.25 per entry.

6. Do the trades match the book?

For each trade print, the checker asks whether the book changed the way the trade implies. Between 3 s before and 10 s after the print, a DEPTH change on the resting side, at the trade's price, should remove at least the trade's size.

Green: consistent within 3 s. Amber: late, within 10 s (4). Red: unexplained (30, of which 12 overnight before the recorder fix).

The matching DEPTH change usually arrives about a millisecond before the trade print, so the two look like they are published in the same batch, DEPTH first. Most of the remaining unexplained trades printed at a price that never appeared as a level on the published book, while other levels on that side shrank. That is a question for the venue, not a conclusion: is a trade's price per fill, or one price per taker order? An order that sweeps several levels and reports one average price would explain most of them.

7. Grading anyone's order-book client

The tape knows the correct book after every update, so it can grade any program that builds books from this feed. The kit has a readable reference builder and a harness that talks to a client in any language over a line protocol. The harness sends one DEPTH message per line. The client answers with its book's state: building, stale, or valid with every level. Each valid book is compared with the tape's.

On recorder 1's own real stream (23,818 DEPTH messages, all twelve books), the reference builder matched the tape on all 23,723 books it reported valid. Then I wrote five broken clients, one for each mistake this feed makes easy:

Broken clientOn the real stream
Adds update sizes instead of replacing themCaught: NVDAC bid 165.516 shows 0.266, the tape has 0.133

Uses the book before SNAPSHOT_COMPLETENot caught here: every real snapshot arrived as one message. The kit catches it on a two-part synthetic snapshot.

The last row is honest about what one day of data can show: a test only catches a bug if the data exercises it.

8. Check a book yourself, in your browser

The verifier can export one book at one moment as a 2.8 KB proof bundle: the book's levels, its log entry, 17 Merkle proof hashes, a signed head, and the three public keys. It writes the bundle only after the whole segment has verified. The proof page recomputes everything with your browser's WebCrypto and trusts only the key fingerprints built into it:

Open the proof page →
The real NVDAC-USDC book just after update 173921. One self-contained file with no network requests. Press "Change one bid size" and watch it fail at inclusion: one altered size no longer leads to the signed root.

A bundle that brings its own keys fails at keys. Every 64-bit value travels as a decimal string, because JSON numbers lose precision above 253, and a proof that rounds a size is no proof.

9. Two machines left

On the evening of 2026-11-12, NUC2 started returning input/output errors and then stopped accepting connections. It has not come back. The other two machines kept recording, and two complete, linked segments from 2026-11-13 (12:01 to 19:13 UTC, through the US open) verify with voters 1 and 2 signing every head. Two of three is the quorum the design asks for.

The run ended at 19:13 UTC, and the archive shows the likely cause. The last head file in the segment is empty: 0 bytes, written at 19:13:23, and NUC1's disk is full today. The voter publishes a head by writing a temporary file and renaming it into place:

void atomic_write(const std::filesystem::path& path, const std::string& text) {
    const auto tmp = path.string() + ".tmp";
    {
        std::ofstream out(tmp, std::ios::binary | std::ios::trunc);
        out << text;              // unchecked: a full disk writes nothing
    }
    std::filesystem::rename(tmp, path);  // publishes it anyway
}

The rename is atomic, but nothing checks that the write succeeded. The verifier refuses the empty head ("unreadable head"), which is the right answer. With that one file set aside, the other 191 heads verify. The fix is to check the write and fsync before renaming, and to alert on disk space before it runs out. I've recorded it (D-67) and left it for the next round. Here the proof system caught a bug in the code that writes the proofs.

10. How I know it works

  • 16 test suites cover the reducer against the independent reference, the replica under restarts and slow or lossy links, the recorder against a scripted feed that behaves like the real one (including its one-request-at-a-time rule), the watchdog, rotation, the report, the proof page and the book kit.
  • A mutation suite plants 34 bugs, among them closing a verdict one tick late, majority-voting divergent copies, skipping the HMAC check, accepting a corrupt log, and resending without back-off. All 34 are caught.
  • Symbol checks prove at link time that the reducer touches no clock, file or socket, and that no tape binary links any order-entry or signing code.
  • Reproducible outputs. Rerunning the report on the archived segments produced a byte-identical summary.json, and the proof bundle and page also came out byte-identical.

The test map is also honest about the gaps: of the 92 test cases in the design, 49 are covered, 22 partly and 21 not yet.

What I took away

  • A network you share is part of your system. Every serious bug here came from home Wi-Fi, not from the logic. Give every loop that sends a ceiling that holds even when the network misbehaves.
  • Read the feed before trusting the docs. A short capture and the first live runs changed the verdict key three times and found a field the spec names wrongly.
  • Make every claim checkable, including the uncomfortable ones. The verifier reports its own stops, the kit admits the trap it couldn't catch, and the signed log exposed the bug that ended its own run.

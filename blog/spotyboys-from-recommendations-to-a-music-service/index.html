SpotyBoys: Turning a Music Recommender into a Service

2026-10-29·Vishal Jha·GitHub Source

During my spring semester at NYU Tandon, I worked on SpotyBoys, a music recommendation system, with Dawei Sun and Yonghyeon Shin for our Machine Learning System Engineering & Operation class. We wanted to connect a recommendation model to something a person could actually use: choose music, listen, skip a track, and get another queue.

I enjoyed working on the space between the model and the application. A ranked list of track IDs looks like a finished result until the player cannot find those tracks, the next request repeats the same artists, or the service quietly falls back while its health endpoint still says everything is fine.

This post walks through the system we built together. My contributions included the serving stack, playback integration, deployment work, serving monitoring, promotion checks and a concurrent load-test harness. The recommender and training pipeline were team work; the repository history records contributions from all three of us.

The problem beyond ranking songs

The model answers a narrow question: given a listener’s history and current session, which candidate tracks should come next? The application has more obligations. It needs an authenticated user, a playable catalog, a consistent session, a player that reports what happened, and a way to update the model without treating every training run as ready to serve.

We used Navidrome for the music player and UI, with patches for a Recommendations page and playback-event capture. A Python FastAPI service handles recommendations and application state. PostgreSQL stores durable records, Redis supports runtime state, and nginx provides the browser-facing entry point. Docker Compose assembles the service stack. GPU training lives separately, with MLflow tracking and an Airflow DAG that invokes training over SSH.

Retrieve a small pool, then rank it

The pipeline separates candidate retrieval from ranking. Retrieval narrows the catalog to a manageable pool. Ranking spends more computation deciding the order within that pool. Policy filtering then makes the result suitable for playback.

  1. Offline artifacts: Item2Vec track embeddings, session and playlist co-occurrence matrices, user preference centroids and popularity scores.
  2. Candidate retrieval: tracks related to the recent session, tracks near the listener’s longer-term preferences, and popular tracks for coverage.
  3. Session ranking: a GRU uses the session prefix to score the candidates.
  4. Playback policy: remove unavailable, recently seen or disliked tracks and diversify the queue by artist.

The retriever allocates up to 100 candidates to co-occurrence, 80 to preference nearest neighbours and 20 to popularity, then deduplicates and caps the pool at 200. These are configured candidate limits, not measured throughput. Popularity also helps when a new listener has little history.

The ranker uses 128-dimensional embeddings and a two-layer GRU. It combines a session representation, a long-term preference vector, a candidate embedding and three similarity features. An MLP produces the candidate’s score. The intuition is straightforward: a listener’s general taste matters, but so does what they are listening to right now.

One implementation detail matters when describing this honestly: the model supports positive, neutral and skip labels, but the serving adapter at the reviewed revision passes the recent prefix to the real runtime with neutral labels. Playback feedback is collected for the data loop; that does not mean every live ranking request already makes full use of it.

A track ID is not yet a playable song

The training artifacts and media player have different identifiers. A track can exist in an embedding table and still be absent from the music library, or lack a valid Navidrome mapping. Sending that ID to the browser does not produce music.

The catalog-sync worker maps the library into a playable catalog. The serving pipeline intersects ranked IDs with that catalog, then the media integration uses the corresponding Navidrome identity. This makes the catalog mapping part of the recommendation contract. A model can load successfully and still return no usable songs if those namespaces disagree.

I added a requirement for the full ML runtime so a deployment intended to exercise the real retriever and ranker would not silently substitute the lightweight fixture path. The repository retains fixtures for tests, but the serving mode can refuse to initialize without the required runtime. That distinction made debugging more concrete: “the API responded” and “the intended model ran” became separate checks. See the serving pipeline.

Queue construction needed attention too. A list dominated by one artist, or a refresh that repeats recently recommended tracks, can be technically valid and still feel broken. Artist diversification, recent-track tracking and playback-triggered refreshes belong in the application behaviour around the score.

A listening session has a lifecycle

To retrain from usage, we needed to record what the listener actually did. A recommendation impression is different from a playback start, and a start is different from a completed listen.

The Navidrome event bridge assigns a playback_id to a physical play and reuses it for the terminal skip or completion event. The backend can insert the start and update that same play instead of counting the lifecycle as unrelated listening events. The exported listening fraction supplies a training label. Those labels are useful proxies for engagement, not proof that a listener liked or disliked a song.

A delta-export worker writes session and user-related Parquet files to object storage and records a checkpoint. Its configured loop defaults to once a day; the retraining trigger defaults to 1,000 new complete-play events. Airflow then invokes the GPU training pipeline. These values describe the implementation, not a claim that we had 1,000 daily active listeners.

The training branch merges exported deltas with the original 30Music snapshot, rebuilds retrieval artifacts and trains the ranker. MLflow records runs, and a promotion step produces a versioned serving bundle. The important connection is that training produces an artifact the service knows how to load, with enough metadata to identify which version is active.

A successful response can still hide a broken model

My monitoring work started with a simple problem: a service may return HTTP 200 while serving fallback recommendations on every request. A dashboard showing only uptime would miss the loss of personalization.

I implemented explicit serving states for conditions such as a missing model, a pipeline exception, an insufficient playable catalog and an operator-selected degraded mode. The response carries the fallback state and reason. Where the catalog permits it, the service can return a deterministic playable fallback instead of failing the whole request.

That is a trade-off. The listener gets a queue, but it may be less personalized. The system needs to expose that difference rather than report fallback as normal model performance. The state decision code and its tests make the behaviour inspectable.

QuestionEvidence the service records
Did the intended model serve this request?Model version, fallback state, reason and pipeline error
Did it return usable recommendations?Candidate, playable and returned-item counts
Was serving responsive?Pipeline and total latency, aggregated into time windows
Is there enough evidence to act?Request count and an explicit insufficient-sample state
Why was a model accepted or rejected?Persisted promotion and rollback decisions

Request telemetry is persisted in PostgreSQL and aggregated for Grafana. Telemetry-write exceptions are caught so an observability failure does not itself fail recommendation serving. The cost of that choice is that missing metrics must not be interpreted as a healthy service.

The rollback evaluator waits for a minimum request count before evaluating thresholds. With too few requests, it records insufficient evidence. With enough evidence, it can recommend rollback or mark a degradation condition. It does not automatically swap the serving bundle: the checked-in worker leaves that mutation manual, even if the automatic-rollback flag is requested.

Training success and deployment approval are different decisions

On the GPU training branch, automatic promotion compares a composite ranking score and validation loss against the baseline. The configured gate accepts a composite score of at least 99% of baseline and a loss no more than 105% of baseline. These are engineering tolerances, not a statistical guarantee that users will prefer the candidate.

The serving side separately checks bundle validity, an approval record and model-version consistency before activation. There is an explicit override option, so this is an operational guard with a documented escape hatch. It should not be described as an unbypassable security boundary. The two parts are visible in the training promotion script and serving activation gate.

What I learned, and what I would improve

The most useful part of this project was learning to debug the connections: training IDs versus media IDs, browser authentication versus API authentication, model availability versus service availability, and a completed training run versus a deployable version.

A concrete example came from the load-test harness. The browser-facing nginx path read a session cookie, while the initial test sent an Authorization header. The fix made the harness use the same cookie mechanism as the browser and added a bootstrap check. Otherwise, an authentication failure could be mistaken for a recommendation-serving performance problem.

The repository includes tests for playable-only recommendations, event idempotency, fallback behaviour, insufficient monitoring samples and promotion checks. Those are useful contract tests. They are not a substitute for evaluating the trained model, measuring a representative workload or running the whole infrastructure. I am not claiming a production latency number or recommendation-quality improvement from the presence of those tests.

For a next iteration, I would focus on carrying actual feedback labels into live ranking, retaining reproducible model-quality and load-test results, and completing a tested rollback execution path. I would also harden the classroom deployment’s authentication, TLS and administrative access before treating it as a public service.

SpotyBoys gave me a practical reason to learn the engineering around ML: getting the right data into the model, the right artifacts into the service, and enough evidence out of the service to understand when it stopped doing what we intended.
